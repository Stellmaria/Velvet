# Перенос Velvet на сервер и облачные модели

## Целевая архитектура

- Linux VPS запускает PostgreSQL, Velvet Bot и Hermes Agent.
- Ролевая и vision-language модели вызываются через BYESU по OpenAI-compatible API.
- Codex работает на сервере от отдельного пользователя и создаёт изменения только через Git-ветки и pull request.
- Hermes координирует диагностику, постановку задач Codex и проверку результатов, но не получает production `.env`, Docker socket или прямую запись в рабочий каталог бота.
- GitHub является источником истины для кода, PostgreSQL — для данных и памяти РП, Telegram Storage — для крупных технических артефактов.

## Этап 1. Подготовка репозитория

1. Слить PR с cloud-first конфигурацией.
2. Убедиться, что `docker-compose.yml` не содержит Ollama.
3. Проверить, что `.env`, `.env.hermes`, Codex auth и приватные ключи игнорируются Git.
4. Запустить tests, type check, Docker build, backup restore drill и project notes contract.
5. Не удалять локальные Qwen-модели до успешного серверного smoke-теста.

## Этап 2. Подготовка VPS

Рекомендуемая минимальная конфигурация без локального инференса:

- Ubuntu 24.04 LTS;
- 6–8 vCPU;
- 16 ГБ RAM минимум, 24 ГБ комфортно для Chromium и задач Hermes;
- 120–200 ГБ SSD/NVMe;
- Docker Engine с Compose plugin;
- отдельный непривилегированный пользователь `velvet`;
- SSH только по ключам, root login и password authentication отключены;
- UFW: наружу открыт только SSH и, при необходимости, HTTPS reverse proxy.

PostgreSQL не публикуется в интернет. Telegram-бот работает через long polling, поэтому входящий HTTP-порт ему не требуется.

## Этап 3. Секреты

Создать на сервере отдельные файлы:

- `.env` для Velvet Bot;
- `.env.hermes` для Hermes;
- `~/.codex/auth.json` пользователя Codex;
- `~/.codex/config.toml` пользователя Codex;
- Hermes config и SOUL внутри его постоянного volume.

Не использовать один Telegram-токен для Velvet и Hermes. Не отправлять секреты в Telegram, GitHub issue, PR, логи или модельный контекст.

## Этап 4. PostgreSQL

1. Остановить локальный бот, чтобы база перестала изменяться.
2. Создать финальный проверенный dump.
3. Передать dump на сервер через защищённый канал.
4. Запустить только PostgreSQL.
5. Восстановить dump и проверить число основных таблиц и записей.
6. Запустить приложение, чтобы применить `z003_roleplay_sessions.sql` и остальные миграции.
7. Создать серверный backup и провести restore drill в отдельной тестовой базе.

## Этап 5. Выбор облачных моделей

Не вписывать названия моделей по памяти или рекламному описанию. Сначала запросить фактический список моделей BYESU и выполнить короткие live-тесты.

### RP-модель

Проверить:

- следование длинному канону;
- сохранение голосов нескольких персонажей;
- устойчивость на 20–30 последовательных ходах;
- длину и литературное качество сцены;
- отсутствие нежелательных отказов в законном личном взрослом RP;
- цену одного типичного хода;
- скорость первого токена и полного ответа.

### VL-модель

Проверить на реальных задачах Velvet:

- точное описание позы и композиции;
- извлечение палитры, света, окружения и объектов;
- сравнение результата с референсом;
- строгое возвращение JSON;
- работу с художественной взрослой обнажённостью без описания запрещённых деталей;
- стабильность на серии изображений.

Включать `AI_TEXT_ENABLED=true` и `AI_VISION_ENABLED=true` только после подтверждения имён моделей и ключа.

## Этап 6. Hermes Agent

1. Создать отдельного Telegram-бота для Hermes.
2. Ограничить доступ одним числовым Telegram ID владельца.
3. Запустить Hermes через профиль `agent`.
4. Установить `approvals.mode: manual`.
5. Дать Hermes отдельный checkout или GitHub-токен минимальных прав.
6. Не монтировать `/var/run/docker.sock`, production `.env`, каталог PostgreSQL и рабочий каталог запущенного бота.
7. Разрешить Hermes собирать безопасные статусы, создавать ветки, запускать тесты и готовить PR.
8. Deployment и миграции выполнять только через отдельную подтверждаемую процедуру.

## Этап 7. Codex

1. Установить Codex CLI от отдельного Linux-пользователя.
2. Скопировать `deploy/codex/config.toml.example` в `~/.codex/config.toml`.
3. Создать `~/.codex/auth.json` с BYESU API key и правами `600`.
4. Использовать отдельные worktree для каждой задачи.
5. Не давать Codex production-секреты и прямой доступ к базе.
6. Hermes проверяет diff и результаты тестов перед передачей PR владельцу.

## Этап 8. Smoke-тест сервера

Обязательные проверки:

- `/start`, архив, сохранение и выдача медиа;
- публикации и фоновые workers;
- `/rp_status`, `/rp_prompt`, `/rp` и продолжение истории после рестарта;
- один VL-анализ и один повтор после временной ошибки API;
- Telegram Storage upload/download;
- backup и restore drill;
- перезапуск контейнеров и автоматическое восстановление;
- Hermes получает команду только от владельца;
- Codex создаёт тестовую ветку без доступа к production `.env`.

## Этап 9. Отключение локальной системы

Только после успешного smoke-теста:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/remove_local_qwen.ps1
powershell -ExecutionPolicy Bypass -File scripts/remove_local_qwen.ps1 -Execute -StopOllama
```

Затем:

1. Проверить оставшиеся Ollama-модели и manifests.
2. Удалить Ollama из автозапуска Windows.
3. Остановить старый Windows Supervisor.
4. Архивировать последний локальный `.env` в зашифрованное хранилище.
5. После контрольного периода удалить ненужные модельные каталоги вручную.
6. Не удалять локальную базу и резервные копии до подтверждения нескольких успешных серверных backup-циклов.

## Следующий рефакторинг

После стабилизации облачного VL-контура удалить или переименовать provider-specific наследие:

- `ollama_vision.py`;
- `ollama_recovery.py` и Supervisor-команды Ollama;
- `local_ai_runtime.py` и глобальный local-AI lock;
- `WorkspaceQwen*`, `qwen_*` команды и тексты интерфейса;
- тесты и документацию локального model bundle;
- Windows Task Scheduler bootstrap, заменив его Linux deployment-контуром.

Этот рефакторинг должен идти отдельным PR после живой проверки облачной VL-модели. Иначе можно одновременно удалить старый двигатель и обнаружить, что новый существует преимущественно в маркетинговом воображении.
