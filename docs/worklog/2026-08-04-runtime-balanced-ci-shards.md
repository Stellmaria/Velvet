## Перед началом

### Цель

Сократить время обязательного GitHub Actions workflow `tests` без уменьшения количества тестов, отключения PostgreSQL-интеграций или ослабления required status checks.

### Исходный контекст

В репозитории уже работают четыре параллельных unittest-шарда, однако файлы распределялись по размеру исходного Python-кода. В последнем успешном прогоне тестовая часть шардов заняла примерно `32.1 / 15.7 / 28.1 / 18.0` секунды. Размер файла оказался слабым приближением для PostgreSQL-, subprocess- и repository-inventory-тестов, поэтому два runner завершались существенно раньше самого медленного.

### Планируемый объём

- сохранить четыре параллельных PostgreSQL-шарда и существующий workflow contract;
- добавить измеренные длительности наиболее тяжёлых тестовых файлов;
- использовать измеренное время как основной вес при детерминированном greedy-распределении;
- оставить безопасный fallback по размеру исходника для новых и пока не измеренных файлов;
- добавить regression-тесты покрытия, валидности duration hints и разнесения тяжёлых файлов.

### Критерии готовности

- каждый параллельный тестовый файл назначается ровно одному шарду;
- четыре самых тяжёлых измеренных файла попадают в разные шарды;
- устаревшая или некорректная запись duration hints останавливает preflight;
- workflow `tests`, type check, security и project notes проходят;
- фактический разброс времени тестовой части шардов уменьшается относительно исходного прогона.

### Риски и ограничения

- длительности GitHub-hosted runner изменяются между запусками и регионами;
- статические hints требуют обновления после существенного изменения тяжёлых тестов;
- fallback по размеру остаётся приближением для новых файлов до накопления измерений;
- эта оптимизация не устраняет общую стоимость запуска runner, Python и PostgreSQL.
