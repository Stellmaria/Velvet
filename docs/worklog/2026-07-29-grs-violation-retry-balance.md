# 2026-07-29 — повтор после GRS violation и живой баланс

- Дата: 2026-07-29
- ID: grs-violation-retry-balance
- Линия/фаза: Мяу / Nano Banana через GRS AI
- Статус: `завершено`
- Ветка: `agent/grs-violation-retry-balance`, follow-up `agent/grs-violation-details-hide-mature`
- Базовый commit: `cd7bad1cf3626122da2401f18fd484b54f594f40`

## Перед началом

### Цель

Распознавать ответ GRS `violation` как отказ модерации, автоматически выполнить один повтор, восстановить отображение текущего баланса и показывать владельцу точную причину блокировки, когда провайдер действительно её возвращает.

### Исходный контекст

GRS возвращал terminal status `violation`, которого не было в таблице состояний клиента. Поэтому ответ превращался в `KieProtocolError`, очередь считала его неизвестным протокольным состоянием и завершала задачу без повтора. Проверка баланса использовала только один старый endpoint и ограниченный набор полей ответа, поэтому карточка показывала «не удалось проверить». После первого исправления интерфейс всё ещё выводил внутреннюю метку `Mature`, хотя для Nano Banana она не управляет GRS-модерацией, и не показывал вложенные поля причины отказа.

### Планируемый объём

- преобразовать moderation-status GRS в типизированную ошибку provider-задачи;
- выполнить один автоматический повтор после первого `violation`;
- остановить кампанию после второго `violation`;
- не использовать общий лимит 50 как число moderation-повторов;
- добавить резервный endpoint проверки API-key balance;
- показывать живой баланс после окончательной остановки;
- извлекать provider-supplied `message`, `reason`, `details`, `blockedReason`, `category`, `code` и родственные поля;
- явно сообщать, когда GRS не передал конкретную причину;
- убрать внутреннюю метку `Mature` из пользовательских сообщений Мяу;
- добавить регрессионные тесты.

### Критерии готовности

- `violation` больше не отображается как неизвестное состояние;
- первая блокировка вызывает ровно один повтор;
- вторая блокировка завершает задачу;
- остальные временные ошибки сохраняют прежнюю retry-политику;
- баланс читается хотя бы через один из двух официальных маршрутов;
- причина отказа показывается только из реального ответа GRS, без догадок;
- при status-only `violation` интерфейс честно сообщает об отсутствии деталей;
- `Mature` не выводится в карточках запроса, ожидания, результата и ошибки;
- API key не появляется в пользовательском сообщении;
- CI проходит.

### Риски и ограничения

- повтор после `violation` ограничен одной дополнительной отправкой;
- суммарно допускаются две provider-попытки для одного запроса;
- бесконечный цикл по общему лимиту 50 запрещён;
- GRS может вернуть только `status=violation` без категории или объяснения, и тогда точную причину определить невозможно;
- внутренний content mode сохранён для обратной совместимости Seedream, но больше не показывается владельцу как действующая настройка Banana;
- фактическое возвращение кредитов может отразиться у провайдера с задержкой;
- CI не выполняет оплачиваемый запрос к GRS.

## После завершения

### Фактически сделано

- `violation`, `content_violation`, `moderation_violation` и `moderated` преобразуются в типизированный `KieTaskFailed`;
- первая модерационная ошибка возвращает задачу в очередь на один повтор;
- после второй модерационной ошибки очередь принудительно завершает кампанию;
- пользователь видит понятный этап повтора и терминальное сообщение;
- финальное сообщение повторно запрашивает баланс GRS;
- баланс сначала читается через документированный `GET /client/common/getCredits`, затем через резервный `POST /client/openapi/getAPIKeyCredits`;
- парсер поддерживает несколько актуальных названий полей баланса;
- добавлен безопасный рекурсивный разбор вложенных provider-полей причины;
- точная причина показывается в retry и terminal сообщениях, если она присутствует в ответе;
- при отсутствии деталей бот пишет, что GRS не передал конкретную причину;
- строки `Контент: Mature` и пояснения про Mature удаляются из UI Мяу;
- начальная карточка Banana больше не говорит пользователю про Worker и отправку модели в Kie;
- успешная карточка результата также не выводит внутренний content mode;
- API key не выводится в пользовательских ошибках.

### Миграции и совместимость

Миграции PostgreSQL не требуются. Внутренний task type и сохранённые campaign payload остаются совместимыми. Ограничение двух попыток применяется только к GRS moderation violation; остальные временные ошибки используют прежнюю политику очереди. Внутреннее поле `content_mode` остаётся в payload для совместимости существующего Kie/Seedream контура, но скрыто из пользовательского интерфейса.

### Проверки

Добавлены и расширены unit-тесты распознавания `violation`, лимита двух provider-попыток, вложенных reason-полей, status-only отказа без выдуманной причины, очистки `Mature`, актуальной формы ответа баланса и fallback endpoint.
