## Перед началом

### Цель

Сократить ожидание обязательного GitHub Actions workflow `tests` примерно с шести минут, не исключая тесты и не ослабляя защиту `main`.

### Исходный контекст

Существующий workflow запускал весь набор `unittest` последовательно в одном job с PostgreSQL. Последний измеренный прогон занимал 5 минут 53 секунды, из которых сами 1842 теста выполнялись около 2 минут 46 секунд. Каждый новый commit агента вынужденно ждал завершения устаревшего запуска, полный лог загружался даже при успехе, а вывод тестов появлялся только после окончания команды.

### Планируемый объём

- отменять устаревшие запуски одного PR;
- вынести дешёвые проверки в отдельный preflight;
- распределить основной набор тестовых файлов между параллельными runner-ами;
- сохранить изолированный PostgreSQL для каждого параллельного job;
- сохранить итоговый обязательный check `unit-tests`;
- закрепить конфигурацию regression-контрактом.

### Критерии готовности

- каждый тестовый файл выполняется ровно один раз либо в preflight, либо в одном shard;
- четыре shard-job работают параллельно и используют отдельные PostgreSQL service containers;
- устаревший запуск отменяется при новом commit в том же PR;
- логи показываются в реальном времени и сохраняются как artifact только при падении;
- итоговый статус `unit-tests` остаётся совместимым с существующей защитой ветки;
- полный workflow проходит заметно быстрее прежнего последовательного запуска.

### Риски и ограничения

Балансировка использует размер тестового файла как стабильный приближённый показатель времени выполнения. Если отдельный небольшой integration-тест станет существенно медленнее остальных, распределение потребуется уточнить на основании `--durations`. Четыре job потребляют больше суммарных runner-minutes, но сокращают критическое время ожидания разработчиков и агентов.

## После завершения

### Фактически сделано

- в `.github/workflows/tests.yml` добавлены `concurrency` и `cancel-in-progress`;
- добавлен preflight без PostgreSQL и установки зависимостей;
- архитектурный inventory, Telegram navigation inventory и `compileall` выполняются до итогового агрегатора;
- 370 остальных тестовых файлов детерминированно распределяются между четырьмя shard-job;
- каждый shard получает собственный PostgreSQL 16 service;
- удалено обновление `pip`, сохранён dependency cache;
- тестовый вывод проходит через `tee`, включены `--durations` и fail-fast;
- artifacts загружаются только при неуспешном job;
- итоговый агрегатор сохраняет check с именем `unit-tests`;
- добавлен `tests/test_ci_workflow_contract.py`, защищающий ключевые настройки и полноту распределения.

### Проверки

Первый PR-прогон нового workflow успешно выполнил preflight, четыре shard-job и итоговый `unit-tests`. Все 370 параллельных тестовых файлов распределены один раз: shard содержат 93, 92, 93 и 92 файла с почти одинаковым суммарным объёмом исходников. Полный обязательный check завершился примерно за 1 минуту 37 секунд вместо прежних 5 минут 53 секунд.

### Миграции и совместимость

Формат тестов, Python 3.13, PostgreSQL 16 и имя обязательного статуса `unit-tests` сохранены. Изменения не затрагивают runtime бота, базу production или deployment. Миграции базы данных не требуются.

### PR и commit

Изменения подготовлены в ветке `agent/speed-up-ci-tests` и опубликованы в PR #494.

### Незавершённое

После накопления нескольких прогонов можно использовать статистику `--durations` для перехода от балансировки по размеру файла к историческим весам. Это не требуется для текущего ускорения.
