## Перед началом

### Цель

Сократить оставшееся время обязательных GitHub Actions после внедрения четырёх параллельных shard, не ослабляя полный тестовый прогон и не используя production VPS как CI runner.

### Исходный контекст

После первого этапа workflow `tests` сократился примерно с 5 минут 53 секунд до 1 минуты 37 секунд. В измеренном shard 467 тестов выполнялись около 22 секунд, тогда как загрузка Docker-образа PostgreSQL, запуск контейнера, настройка Python и повторная установка зависимостей занимали большую часть оставшегося времени.

GitHub-hosted runner `ubuntu-24.04` уже содержит PostgreSQL 16, отключённый по умолчанию. Для установки Python-зависимостей доступен `uv` с собственным cache, поэтому отдельный Docker service и обычный `pip install` больше не обязательны.

### Планируемый объём

- запускать предустановленный PostgreSQL 16 через systemd внутри каждого GitHub-hosted shard;
- создавать изолированные тестовые роль и базу с прежними полномочиями Docker service;
- заменить `pip install` на закреплённый `uv` в `tests` и `type check`;
- сохранять один общий cache зависимостей для тестовых shard без конкурентной записи четырьмя job;
- загружать mypy artifact только при ошибке;
- закрепить новую конфигурацию regression-контрактами.

### Критерии готовности

- четыре shard продолжают выполнять полный набор тестов;
- PostgreSQL 16 запускается без Docker service container;
- тестовый пользователь сохраняет совместимость с прежним Docker PostgreSQL;
- зависимости устанавливаются через закреплённые версии `setup-uv` и `uv`;
- обязательные проверки `unit-tests`, `type check` и project notes contract зелёные;
- production VPS, Compose и production PostgreSQL не меняются;
- фактическое время CI измерено на PR.

### Риски и ограничения

GitHub может обновлять состав hosted runner, поэтому наличие PostgreSQL дополнительно защищается явной командой запуска и regression-контрактом workflow. Если GitHub когда-либо удалит PostgreSQL 16 из образа, CI упадёт явно, а не переключится незаметно на другую базу. Production VPS намеренно не используется как self-hosted runner: такой runner потребовал бы отдельного пользователя, изоляции, очистки workspace, управления секретами и исключения конкуренции с работающим ботом.

## После завершения

### Фактически сделано

- Docker service PostgreSQL удалён из четырёх тестовых shard;
- каждый GitHub-hosted runner запускает встроенный PostgreSQL 16 через systemd;
- тестовая роль `velvet` создаётся как isolated CI superuser, сохраняя прежние возможности Docker-образа;
- зависимости тестов и bounded mypy устанавливаются закреплённым `uv 0.11.16` через `setup-uv v8.1.0`;
- только shard 0 сохраняет общий cache, остальные shard выполняют только restore;
- mypy artifact загружается только при ошибке;
- выявлен дополнительный bottleneck в package architecture preflight: прежний анализатор повторно обходил полный AST для каждого найденного вызова, литерала и присваивания;
- добавлен совместимый быстрый adapter, который один раз индексирует диапазоны владельцев AST и кеширует поиск по строке;
- preflight продолжает выполнять те же package architecture и Telegram navigation контракты;
- отдельный regression-тест подтверждает совпадение fast owner с прежней narrowest-span семантикой;
- CI-конфигурация, native PostgreSQL, uv и оптимизированный preflight закреплены regression-контрактами.

### Проверки

Итоговый PR-прогон полностью зелёный: `project notes contract`, `type check`, `preflight`, четыре изолированных тестовых shard и агрегированный `unit-tests` завершились успешно.

Фактические измерения:

- полный обязательный workflow `tests`: около 58 секунд от старта первого runner до завершения агрегатора;
- предыдущий результат после первого этапа: около 1 минуты 37 секунд;
- дополнительное сокращение: около 39 секунд, или примерно 40%;
- исходный результат до обоих этапов: около 5 минут 53 секунд;
- общее сокращение: примерно 84%, то есть полный CI стал приблизительно в 6,1 раза быстрее;
- package architecture и Telegram navigation preflight: 8 тестов за 10,701 секунды вместо 81,258 секунды, примерно в 7,6 раза быстрее;
- representative shard: 441 тест за 15,948 секунды;
- установка 24 runtime-пакетов через `uv`: менее одной секунды после подготовки инструмента;
- bounded `type check`: около 11 секунд целиком вместо примерно 21 секунды ранее.

Скачивание бинарника `uv` и выдача GitHub-hosted runner могут колебаться между прогонами, поэтому ориентиром считается измеренное end-to-end время полного workflow, а не длительность одной сетевой операции.

### Миграции и совместимость

Runtime бота, production PostgreSQL, Docker Compose и схема данных не изменяются. Миграции базы данных не требуются. Изменения касаются только GitHub Actions и тестового анализатора архитектуры. Production VPS `144.31.165.142` не изменялся и не подключался как self-hosted runner.

### PR и commit

Изменения опубликованы в PR #495 из ветки `agent/ci-native-postgres-uv`. Итоговый merge commit будет зафиксирован GitHub после принятия PR.

### Незавершённое

Self-hosted runner на production VPS намеренно не создавался. Для безопасного использования собственного сервера потребуется отдельный непривилегированный пользователь или изолированная VM/container, отсутствие production-секретов, ограничения CPU/RAM/IO, очистка workspace и запуск только доверенного кода.

### Следующий шаг

Наблюдать длительность следующих 5–10 прогонов. Историческую балансировку shard по реальному времени добавлять только при устойчивом перекосе одного runner, а не ради ещё одного слоя CI-алхимии без измеримой пользы.
