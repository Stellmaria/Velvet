## Перед началом

### Цель

Сократить оставшееся время обязательных GitHub Actions после внедрения четырёх параллельных shard, не ослабляя полный тестовый прогон и не используя production VPS как CI runner.

### Исходный контекст

После первого этапа workflow `tests` сократился примерно с 5 минут 53 секунд до 1 минуты 37 секунд. В измеренном shard 467 тестов выполнялись около 22 секунд, тогда как загрузка Docker-образа PostgreSQL, запуск контейнера, настройка Python и повторная установка зависимостей занимали большую часть оставшегося времени.

GitHub-hosted runner `ubuntu-24.04` уже содержит PostgreSQL 16, отключённый по умолчанию. Для установки Python-зависимостей доступен `uv` с собственным cache, поэтому отдельный Docker service и обычный `pip install` больше не обязательны.

### Планируемый объём

- запускать предустановленный PostgreSQL 16 через systemd внутри каждого GitHub-hosted shard;
- создавать изолированные тестовые роль и базу с прежними полномочиями Docker service;
- заменить `pip install` на закреплённый `uv` в `tests` и `type check`;
- сохранять один общий cache зависимостей для тестовых shard без конкурентной записи четырьмя job;
- загружать mypy artifact только при ошибке;
- закрепить новую конфигурацию regression-контрактами.

### Критерии готовности

- четыре shard продолжают выполнять полный набор тестов;
- PostgreSQL 16 запускается без Docker service container;
- тестовый пользователь сохраняет совместимость с прежним Docker PostgreSQL;
- зависимости устанавливаются через закреплённые версии `setup-uv` и `uv`;
- обязательные проверки `unit-tests`, `type check` и project notes contract зелёные;
- production VPS, Compose и production PostgreSQL не меняются;
- фактическое время CI измерено на PR.

### Риски и ограничения

GitHub может обновлять состав hosted runner, поэтому наличие PostgreSQL дополнительно защищается явной командой запуска и regression-контрактом workflow. Если GitHub когда-либо удалит PostgreSQL 16 из образа, CI упадёт явно, а не переключится незаметно на другую базу. Production VPS намеренно не используется как self-hosted runner: такой runner потребовал бы отдельного пользователя, изоляции, очистки workspace, управления секретами и исключения конкуренции с работающим ботом.
