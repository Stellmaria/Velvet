## Перед началом

### Цель

Исключить одновременный запуск двух процессов Velvet Supervisor из одной рабочей копии и тем самым предотвратить запуск двух Telegram polling-процессов.

### Исходный контекст

Внутренний lock операций защищал только потоки одного процесса. Два отдельных Supervisor могли одновременно создать runtime, запустить дочерние процессы и затем конфликтовать за Telegram `getUpdates`.

### Планируемый объём

- добавить межпроцессный lock в runtime-каталоге;
- завершать второй Supervisor до создания runtime;
- сообщать PID владельца блокировки;
- восстанавливать работу после устаревшего lock;
- удалять lock только его владельцем;
- покрыть живого владельца, stale-lock и безопасный release тестами.

### Критерии готовности

- второй живой процесс получает предсказуемую ошибку и код завершения;
- аварийно оставшийся lock не блокирует следующий запуск навсегда;
- чужой lock не удаляется при release;
- тесты не требуют отсутствующей в проекте зависимости `pytest`;
- ветка основана на актуальном `main` после PR #328.

### Риски и ограничения

- проверка существования PID зависит от поведения `os.kill(pid, 0)` на целевой ОС;
- файловая блокировка защищает одну рабочую копию и один runtime-каталог, а не все возможные установки Supervisor;
- lock не заменяет штатное завершение дочерних процессов.

## После завершения

### Фактически сделано

- добавлен `SupervisorInstanceGuard` с атомарным созданием `supervisor.instance.lock`;
- PID вычисляется при создании guard, а не при импорте модуля;
- живой владелец блокирует второй запуск с указанием PID;
- повреждённый или устаревший lock удаляется и создаётся заново;
- release удаляет файл только при совпадении PID владельца;
- startup Supervisor обёрнут guard до создания runtime и HTTP-сервера;
- pytest-тесты переписаны на стандартные `unittest`, `tempfile` и `unittest.mock`.

### Миграции и совместимость

Миграции базы данных и изменения конфигурации не требуются. Lock создаётся в существующем runtime-каталоге и удаляется при нормальном завершении.
