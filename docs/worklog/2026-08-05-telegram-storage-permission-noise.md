# Сессия: Telegram Storage backup permissions и deletion log noise

- Дата: 2026-08-05
- ID: `2026-08-05-telegram-storage-permission-noise`
- Линия/фаза: Telegram Storage / production hotfix
- Статус: завершено
- Ветка: `fix/telegram-storage-permission-noise`
- Базовый commit: `cba217e7bad00db56d4764b3f6658b465e230429`

## Перед началом

### Цель

Устранить поток пустых `INFO`-событий `telegram_storage_deletion_result` и
закрепить регрессионным тестом, что ошибка чтения одного backup остаётся локальной
для этого файла и не прерывает обработку следующих резервных копий.

### Исходный контекст

В production-логе почасовая миграция Telegram Storage повторно завершалась с
`PermissionError` при чтении файла
`pre-z032-20260804T183304Z-ca860bdf038c.dump`. Тот же проход создавал сотни
одинаковых событий удаления с `planned=0`, `deleted=0`, `issues=0` и
`freed_bytes=0`.

Актуальный `main` уже оборачивает обработку каждого backup отдельной границей
ошибки внутри `_migrate_backups`. Поэтому фатальный traceback указывает на старый
production-контейнер. При этом `_audit_result` действительно записывал пустой
результат на уровне `INFO` и требовал отдельного исправления.

### Планируемый объём

- понизить полностью пустые deletion-result события до `DEBUG`;
- сохранить `INFO` для планов, удалений, ошибок и освобождённых байтов;
- добавить тест уровней логирования;
- добавить тест изоляции `PermissionError` одного backup;
- не обходить права файлов и не ослаблять deletion policy;
- зафиксировать необходимость обновления production-образа и исправления прав.

### Критерии готовности

- пустой результат удаления не попадает в обычный `INFO`-лог;
- содержательный результат по-прежнему виден на уровне `INFO`;
- `PermissionError` одного backup добавляется в summary;
- после ошибочного backup сервис переходит к следующему объекту;
- права на backup не подменяются небезопасным чтением или `chmod` из приложения;
- обязательные CI checks проходят перед merge.

### Риски и ограничения

- код не может безопасно исправить владельца host-файла из контейнера;
- конкретный unreadable backup останется необработанным до исправления UID/GID
  или режима доступа на сервере;
- production traceback исчезнет только после развёртывания актуального `main`;
- события с реальными ошибками и действиями намеренно сохраняются в `INFO` или
  `WARNING`.

## После завершения

### Фактически сделано

- `_audit_result` выбирает `DEBUG` для полностью пустого результата;
- результаты с планами, удалениями, issues или освобождёнными байтами сохраняют
  уровень `INFO`;
- добавлен тест пустого deletion-result;
- добавлен тест непустого deletion-result;
- добавлен async regression-тест, где первый backup вызывает `PermissionError`,
  а второй всё равно достигает своей обработки;
- подтверждено, что существующий per-backup exception boundary в актуальном
  `main` не требует ослабления.

### Миграции и совместимость

SQL-миграции и схема PostgreSQL не изменены. Публичные интерфейсы удаления не
изменены. Совместимость сохранена: `DeletionResult` и итерационный API остаются
прежними, меняется только уровень пустой audit-записи.

### Проверки

- regression-тест проверяет `DEBUG` для нулевого результата;
- regression-тест проверяет `INFO` для содержательного dry-run;
- regression-тест проверяет продолжение backup-loop после `PermissionError`;
- type check прошёл на первом head PR;
- полный обязательный CI повторно запускается после исправления worklog.

### PR и commit

- PR: #646 `Fix Telegram storage permission isolation and deletion log noise`;
- ветка: `fix/telegram-storage-permission-noise`;
- итоговый merge commit будет создан GitHub после зелёных checks.

### Незавершённое

Кодовый hotfix завершён. На production остаётся обновить контейнер до актуального
`main` и исправить права на конкретный backup-файл. Без серверного изменения прав
этот файл продолжит фиксироваться как частичная ошибка, но не остановит остальные
backup-объекты.

### Следующий шаг

Дождаться зелёных обязательных checks, слить PR #646 в `main`, затем развернуть
обновлённый образ Velvet и исправить владельца или группу unreadable backup на
хосте без использования небезопасного режима `777`.
