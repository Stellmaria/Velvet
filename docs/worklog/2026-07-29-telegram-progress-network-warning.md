## Перед началом

### Цель

Не считать временный разрыв соединения Telegram при обновлении progress-сообщения ошибкой генерации, не мешать очереди GRS и не показывать разговорные safety-отказы модели как техническую причину провайдера.

### Исходный контекст

При попытке GRS Telegram разорвал HTTP-соединение во время `edit_message_text`. Генерация продолжилась, но `friendly_worker` записал `TelegramNetworkError` через `logger.exception`, поэтому центр ошибок создал ERROR с полным traceback. В том же логе GRS вернул разговорную фразу «не могу создавать небезопасные изображения», которая ошибочно отображалась как конкретная техническая причина.

### Планируемый объём

- перехватывать `TelegramNetworkError` отдельно от остальных Telegram API ошибок;
- записывать временный обрыв как WARNING без traceback;
- не задерживать и не останавливать provider-кампанию из-за недоступности Telegram edit API;
- сохранить повторную попытку обновления на следующем progress-событии;
- отбрасывать разговорный safety-отказ как недостоверную диагностику GRS;
- сохранить структурированные provider-коды и категории;
- добавить регрессионные тесты.

### Критерии готовности

- `ServerDisconnectedError` при обновлении прогресса не создаёт ERROR-инцидент;
- warning явно сообщает, что генерация продолжается;
- очередь и provider-задача не зависят от доставки progress-сообщения;
- `IMAGE_SAFETY` и другие структурированные значения сохраняются;
- разговорная фраза «не могу создавать небезопасные изображения» отбрасывается;
- CI проходит.

### Риски и ограничения

- одно progress-обновление может быть пропущено, если Telegram временно недоступен;
- следующее успешное обновление синхронизирует карточку;
- неопределённая платная отправка без task id по-прежнему останавливает кампанию для защиты баланса;
- видимые `Мяу` и задержка 30 секунд в предоставленном логе означают, что запущенный процесс ещё не использовал merge commit с Auf и мгновенным retry.
