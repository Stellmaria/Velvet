## Перед началом

### Цель

Исправить служебный экран балансов, чтобы успешный ответ Byesu отображал доступный долларовый лимит API-ключа вместо сообщения об отсутствии остатка.

### Исходный контекст

Production-проверка с действующим `BYESU_BALANCE_API_KEY` вернула HTTP 200 и payload с `hard_limit_usd`, `soft_limit_usd` и `system_hard_limit_usd`. Текущий код ожидал только несуществующее в этом ответе поле `balance_usd` и подписывал значение как баланс аккаунта.

### Планируемые изменения

- читать `hard_limit_usd` из ответа `/dashboard/billing/subscription`;
- сохранить совместимость с прежним полем `balance_usd` как fallback;
- переименовать показатель в `Byesu · доступно по ключу`;
- обновить безопасные сообщения об ошибках;
- добавить regression-тесты реального формата ответа и подписи.

### Вне объёма

- вычисление общего баланса аккаунта Byesu;
- суммирование лимитов нескольких API-ключей;
- вычитание исторического `total_usage` из текущего лимита;
- изменение production-секретов.

### Критерии готовности

- payload с `hard_limit_usd` преобразуется в долларовое значение;
- legacy payload с `balance_usd` продолжает поддерживаться;
- Telegram не называет лимит ключа балансом аккаунта;
- секреты и сырые ответы провайдера не выводятся пользователю;
- целевые и обязательные CI-проверки проходят.

### Риски и допущения

- `hard_limit_usd` отражает доступный лимит переданного API-ключа, а не общий баланс аккаунта;
- формат Byesu может измениться без версионирования;
- production smoke требует обновления сервера после merge.

## После завершения

### Что сделано

- приоритетным полем успешного ответа стало `hard_limit_usd`;
- `balance_usd` оставлено как совместимый fallback;
- сообщение об отсутствующем значении уточнено до отсутствующего доступного лимита;
- подпись изменена на `Byesu · доступно по ключу`;
- сообщения сетевого слоя приведены к терминологии лимита;
- добавлены regression-тесты для реального payload, fallback и подписи.

### Что проверено

- production-диагностика до изменения: HTTP 200, `hard_limit_usd=10.001866`;
- API-ключ присутствует внутри контейнера и начинается с `sk-`;
- тесты не выполняют реальные сетевые запросы и не содержат секретов;
- обязательные проверки выполняются в PR.

### Что осталось

- обновить production через стандартный deploy script;
- нажать `Обновить балансы` и подтвердить отображение лимита Byesu.

### Решения и компромиссы

- не используется `total_usage`: диагностический запрос охватывал произвольный широкий период, а вычитание из текущего лимита не имеет надёжного контракта;
- показатель намеренно описан как лимит ключа, чтобы не выдавать его за общий баланс аккаунта;
- fallback `balance_usd` сохранён на случай другого совместимого ответа провайдера.

### Важные детали для следующей сессии

- при новом HTTP 401 сначала проверять окружение контейнера и статус API-ключа, не менять endpoint без подтверждённого контракта.
