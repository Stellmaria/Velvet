# Техническое задание: облачный AI-контур, РП, VL и автономный контроль Velvet

Статус: утверждено к поэтапной реализации  
Дата: 2026-07-28  
Проект: `Stellmaria/Velvet`

## 1. Цель

Перенести AI-функции Velvet с локального компьютера в серверный контур так, чтобы:

- два Telegram-бота и PostgreSQL работали постоянно на обычном VPS;
- оплата нейросетей происходила только при реальном запросе;
- обычные изображения анализировались умной облачной VL-моделью;
- чувствительные изображения имели отдельный маршрут без внешней фильтрации провайдера либо через менее ограниченный API;
- ролевая игра работала через отдельную качественную модель с длинным контекстом и постоянной памятью;
- Hermes подключался только при повторных падениях, новых ошибках и сложных инцидентах;
- простые проверки и перезапуски выполнялись без LLM и без расхода токенов;
- ни Hermes, ни Codex не получали root, Docker socket, production-секреты или прямую запись в `main`;
- все расходы учитывались до выполнения запроса и ограничивались дневным и месячным бюджетом.

## 2. Базовые принципы

1. **Постоянно оплачивается только VPS и резервное хранение.**
2. **LLM/VL/RP вызываются по факту.** Нет фоновых запросов ради проверки, что всё ещё существует.
3. **Каскад моделей вместо одной дорогой модели.** Дешёвая модель выполняет основной объём, сильная включается при низкой уверенности, отказе или ручном глубоком анализе.
4. **Сначала механическая автоматика, затем Hermes.** Перезапуск процесса, health-check, проверка БД и диска не требуют нейросети.
5. **Все результаты кэшируются.** Повторный анализ того же изображения той же версией промта не оплачивается повторно.
6. **Секреты хранятся только на сервере.** Ключи не попадают в Git, Telegram, диагностические архивы и сообщения Hermes.
7. **Любое опасное действие требует подтверждения.** Автоматически разрешены только операции из фиксированного реестра.

## 3. Целевая архитектура

```text
Основной VPS
├── Velvet Bot
├── второй Telegram-бот
├── PostgreSQL
├── Supervisor / watchdog
├── Hermes Gateway
├── Codex CLI
├── AI task queue
├── usage ledger / budget guard
├── backups
└── health endpoints

Облачные провайдеры, оплата по запросу
├── BYESU: умная VL и агентные модели
├── RP API: основная и резервная РП
└── optional serverless GPU: собственная VL/RP при необходимости
```

### 3.1. Основной VPS

Минимальный целевой профиль:

- Linux;
- 6–8 vCPU;
- 16–24 ГБ RAM;
- 160–250 ГБ NVMe;
- Docker Compose;
- закрытые внутренние сети между контейнерами;
- внешний доступ только к необходимым health/reverse-proxy endpoints;
- автоматические ежедневные резервные копии PostgreSQL.

На VPS не запускается тяжёлая VL/RP-модель на CPU как основной рабочий контур. Открытые веса могут храниться отдельно, но вычисление выполняется на serverless GPU только при наличии очереди.

## 4. Модельный контур

Точные model ID не фиксируются в коде до живой проверки `/v1/models` конкретного токена. Модели задаются переменными окружения.

### 4.1. Основная VL

Назначение:

- геометрия сцены;
- поза, руки, ноги и перекрытия;
- композиция, ракурс, объектив;
- свет, палитра и окружение;
- сравнение референса и результата;
- структурированный JSON;
- оценка уверенности.

Маршрут:

1. Flash-класс для массового анализа.
2. Pro-класс только при низкой уверенности, повреждённом JSON, сложной сцене или ручном запросе.
3. Модель-судья только при конфликте двух результатов.

### 4.2. Чувствительная VL

Назначение:

- материалы, которые официальная облачная VL отказывается анализировать;
- художественное ню и сложные сцены;
- ручной режим анализа без провайдерского фильтра.

Этапы:

1. Проверить подходящую мультимодальную модель через API с оплатой по токенам.
2. Если качество или процент отказов неудовлетворительны, развернуть открытую VL на serverless GPU с `min_workers=0`.
3. GPU запускается при поступлении очереди и выключается после простоя.

### 4.3. Ролевая модель

Требования:

- русский язык;
- контекст не менее 64K, целевой 128K;
- устойчивое соблюдение канона персонажей;
- длинные сцены и диалоги;
- отдельный системный промт;
- низкая цена на вход и выход;
- приватный режим;
- отсутствие обязательного постоянного GPU.

В запрос передаются:

- постоянный канон;
- актуальное долговременное резюме;
- релевантные воспоминания;
- последние сообщения;
- текущая реплика.

Полная история не пересылается на каждом ходе. Старые сообщения периодически сворачиваются в резюме.

### 4.4. Hermes и Codex

Hermes является оркестратором, а не отдельной платной моделью. Расход возникает только при вызове подключённого LLM.

Роли:

- дешёвая модель: классификация инцидентов, краткие сводки, сжатие логов;
- сильная модель: сложный анализ повторяющихся ошибок;
- Codex: подготовка исправления кода в отдельной ветке и draft PR;
- CI: окончательная проверка вместо повторного LLM-«одобрения».

## 5. Маршрутизация VL

```text
Новое изображение
→ SHA-256 и поиск кэша
→ нормализация размера и удаление EXIF
→ определение категории

обычное
→ Flash VL
→ confidence >= threshold и JSON valid
→ сохранить результат

низкая уверенность / сложная сцена
→ Pro VL
→ сохранить исправленный результат

чувствительное / отказ
→ sensitive VL
→ сохранить результат

конфликт результатов
→ модель-судья
```

Целевые ограничения:

- Pro VL: не более 10–15% массовой партии;
- один повтор запроса после сетевой ошибки;
- максимум 800–1200 выходных токенов для обычного анализа;
- не более двух параллельных облачных VL-запросов на старте;
- serverless GPU worker: `0 → 1 → 0`.

## 6. Массовый импорт 2 000–5 000 изображений

Перед вызовом моделей:

1. вычислить SHA-256;
2. удалить дубли;
3. найти уже существующий анализ;
4. сформировать уменьшенную копию;
5. удалить EXIF;
6. разбить очередь на обычную, чувствительную и сложную;
7. показать владельцу оценочный максимальный бюджет;
8. потребовать подтверждение запуска партии.

Для каждой задачи сохраняются:

- hash изображения;
- тип анализа;
- provider и model ID;
- версия модели;
- версия промта;
- confidence;
- input/output tokens;
- рассчитанная стоимость;
- latency;
- статус и причина fallback;
- итоговый JSON.

## 7. Бюджетный контроль

### 7.1. Лимиты

Обязательные параметры:

- дневной лимит;
- месячный лимит;
- максимальная стоимость одного запроса;
- резерв бюджета для аварийного Hermes;
- отдельные лимиты по назначению: VL, RP, Hermes/Codex;
- hard stop при превышении;
- soft warning на 70%, 85% и 95%.

Проверка выполняется **до запроса** по оценочной стоимости и **после запроса** по фактическому usage.

### 7.2. Команды владельца

Целевые команды:

```text
/ai_budget
/ai_usage
/ai_cost_today
/ai_cost_month
/ai_queue
/ai_pause
/ai_resume
/ai_models
```

### 7.3. Кэш

Ключ кэша:

```text
content_hash + analysis_type + model_id + prompt_version
```

При совпадении ключа API повторно не вызывается.

## 8. Supervisor и Hermes при инцидентах

### 8.1. Уровень 1: без LLM

Supervisor постоянно и бесплатно проверяет:

- процесс бота;
- контейнерный health-check;
- PostgreSQL;
- свободный диск;
- память;
- зависшие workers;
- размер очереди;
- время последней успешной операции.

Автоматически разрешено:

- перезапустить конкретный сервис;
- повторить health-check;
- остановить зависшую очередь;
- переключить AI provider на заранее настроенный fallback;
- уведомить владельца.

### 8.2. Уровень 2: Hermes

Hermes вызывается только если:

- бот упал несколько раз в restart window;
- открыт crash loop;
- после перезапуска health-check не восстановился;
- появилась новая сигнатура исключения;
- миграция, update или backup завершились ошибкой;
- очередь зависла или резко выросла;
- произошёл повтор одного инцидента после автоматического действия.

Hermes получает ограниченный пакет:

- тип инцидента;
- код завершения;
- последние строки логов;
- crash count;
- commit/branch;
- состояние Supervisor;
- разрешённый список действий;
- запрет на root, секреты, удаление БД и прямой push в `main`.

Hermes API используется через внутренний endpoint `POST /v1/runs`. Запрос отправляется асинхронно, чтобы Supervisor не блокировал monitor loop.

### 8.3. Уровень 3: Codex

Codex запускается только если Hermes определил, что требуется изменение кода. Codex:

1. создаёт отдельный worktree/ветку;
2. вносит ограниченное исправление;
3. запускает тесты;
4. создаёт draft PR;
5. не выкатывает изменение в production автоматически.

## 9. Безопасность

Hermes запрещено предоставлять:

- `/var/run/docker.sock`;
- production `.env`;
- ключи БД и API;
- root/sudo;
- каталог работающего приложения на запись;
- право прямого изменения `main`;
- доступ ко всем репозиториям пользователя.

Hermes получает собственный persistent volume, отдельный Telegram-токен, отдельный API key и fine-grained GitHub token только для `Stellmaria/Velvet`.

Логи перед передачей в Hermes очищаются от:

- Bearer/API токенов;
- Telegram bot tokens;
- DSN и паролей PostgreSQL;
- содержимого переменных с `KEY`, `TOKEN`, `SECRET`, `PASSWORD`;
- приватных URL с credentials.

## 10. Мониторинг полного падения VPS

Hermes на том же VPS не может обнаружить смерть собственного VPS. Требуется внешний uptime-monitor:

- проверка публичного `/health` каждые 1–3 минуты;
- Telegram/email-уведомление;
- при поддержке хостером: вызов reboot API;
- после запуска VPS systemd поднимает Docker;
- Supervisor проверяет все сервисы;
- Hermes получает incident после восстановления.

## 11. Ожидаемая стоимость

Постоянная часть:

- VPS и backups: ориентир 2 000–3 900 ₽/мес.

По факту использования:

- РП: ориентир 200–1 250 ₽/мес. для одного пользователя;
- текущая VL после импорта: 100–500 ₽/мес.;
- Hermes: обычно 50–300 ₽/мес.;
- первичная партия 2 000–5 000 изображений: ориентир 1 000–3 500 ₽ с каскадом;
- serverless GPU не является обязательным и оплачивается только при запуске.

Целевой жёсткий лимит:

- первый месяц: до 9 000 ₽;
- обычный месяц после импорта: до 5 000 ₽.

## 12. Этапы реализации

### Фаза 1. Control plane

- бюджетный guard и модели данных usage;
- env-конфигурация лимитов;
- внутренний Hermes API;
- вызов Hermes при crash loop;
- редактирование секретов в логах;
- status Supervisor с состоянием Hermes;
- тесты.

### Фаза 2. Usage ledger

- PostgreSQL-таблицы AI usage и task queue;
- запись фактических токенов и стоимости;
- дневные/месячные агрегаты;
- команды владельца.

### Фаза 3. VL router

- Flash/Pro/sensitive маршруты;
- confidence policy;
- кэш по hash/model/prompt;
- пакетный импорт;
- бюджет до запуска партии.

### Фаза 4. RP router

- основной и fallback provider;
- лимиты ответа;
- резюме памяти;
- стоимость хода;
- мониторинг качества и отказов.

### Фаза 5. Serverless GPU

- подключается только после теста облачной sensitive VL;
- worker scale-to-zero;
- очередь и idle shutdown;
- автоматический fallback без постоянной аренды GPU.

### Фаза 6. Production migration

- выбор VPS с допустимыми правилами контента;
- перенос PostgreSQL;
- smoke tests;
- backup/restore drill;
- внешний uptime monitor;
- удаление локальных моделей только после успешной проверки сервера.

## 13. Критерии приёмки

Система считается готовой, когда:

1. оба бота автоматически восстанавливаются после обычного падения без LLM;
2. Hermes получает incident только после заданного порога повторных падений;
3. секреты не попадают в payload Hermes;
4. превышение бюджета блокирует новый AI-запрос;
5. повторный анализ изображения берётся из кэша;
6. массовая партия требует подтверждения оценочной стоимости;
7. RP использует резюме и ограниченную историю;
8. Pro VL не вызывается для всей партии;
9. serverless GPU масштабируется до нуля;
10. Codex создаёт draft PR, но не выкатывает код самостоятельно;
11. полный restore PostgreSQL проверен на отдельной БД;
12. владелец получает Telegram-уведомления об инцидентах и расходах.

## 14. Не входит в первую фазу

- окончательный выбор конкретных model ID без живого API-теста;
- покупка постоянного GPU;
- автоматическое слияние PR от Hermes/Codex;
- удаление локальных весов до завершения server smoke test;
- хранение production-секретов в репозитории;
- передача Hermes полного доступа к серверу.
