# Проектный контракт Hermes Coder: Romatic Club Max

Личность агента задаётся в `SOUL.md`. Этот файл содержит только проектные правила и процедуры.

## Граница проекта

- Работай только над `Stellmaria/romatic_club_bot_max` в текущем рабочем каталоге процесса, который runner назначил конкретному run.
- Текущий `cwd` является единственным task checkout. Не переходи в `/workspace`, `/workspace-base`, chat workspace, соседний run или другой checkout.
- Не переключайся на Velvet или другой репозиторий.
- Не продолжай старую задачу, если пользователь назвал другую задачу или другой объект.
- Перед изменением зафиксируй репозиторий, ветку, задачу, затрагиваемые файлы и критерий готовности.
- Сначала прочитай репозиторный `AGENTS.md` либо `.hermes.md`, если он существует, и обязательную проектную документацию из текущего `cwd`.
- Если текущий `cwd` не является checkout `Stellmaria/romatic_club_bot_max`, остановись и сообщи точную причину.

## Git

- Не работай напрямую в default branch.
- Создавай отдельную ветку для каждой изменяющей задачи.
- Не выполняй force-push, reset чужих веток, удаление веток или merge.
- Перед коммитом показывай краткий diff, запускай релевантные тесты и проверяй `git status`.
- Не включай секреты, production env, дампы, токены и диагностические архивы в Git.
- Для одной оркестрированной задачи создавай не более одной ветки и одного pull request.
- Чистый `git status` после commit не означает отсутствие mutation: HEAD, refs, branch и PR являются частью audit evidence.

## База данных и миграции

- Production PostgreSQL доступен только read-only ролью.
- Не пытайся обходить `default_transaction_read_only`, менять роль или подключаться владельцем базы.
- Сначала изучай фактические legacy-данные и схему, затем готовь миграцию или контролируемое изменение в ветке.
- Не редактируй уже применённые миграции.
- Новые миграции должны быть последовательными, повторно применимыми в предусмотренных проектом границах и сохранять переносимые SHA-256 проверки.
- Constraint нельзя добавлять поверх исторических данных без предварительной проверки совместимости и безопасной стратегии нормализации.
- Production-изменения данных и применение миграций выполняются отдельно после проверки и явного разрешения владельца.

## Безопасность

- Разрешённая область записи: только effective per-run workspace, совпадающий с текущим `cwd`.
- Shared/base checkout является read-only источником и не является task workspace.
- Не ищи секреты и не исследуй соседние контейнеры, production volumes, Docker socket или системные каталоги.
- Не запускай Docker, systemd, deployment, restart, update или rollback.
- Не запускай платные или внешние действия без необходимости задачи.

## Оркестрированные задачи

- Задача с заголовком `ОРКЕСТРИРОВАННАЯ TIER-AWARE ЗАДАЧА` поступает через central router.
- Direct owner path и делегирование Каэлем используют одну identity, один runner, один ledger и одну workspace policy. Различается только trusted source marker.
- Строго сохраняй переданный Task ID и не смешивай его с другой работой или Telegram-сессией.
- Работай только в effective path, который runner добавляет непосредственно перед задачей. Не заменяй его статическим путём из памяти или документации.
- Подготовь код, тесты, документацию, отдельную ветку и один PR только если mutation policy это разрешает.
- Для `read_only` не создавай branch, commit, push или PR.
- Не сливай PR и не выполняй production-действия.
- В финале обязательно верни ровно один JSON-объект по установленной
  `output.schema.json`. Пустое значение передавай пустой строкой:

```json
{
  "status": "completed|blocked|failed",
  "branch": "",
  "pr": "",
  "tests": [],
  "blocker": "",
  "memory_candidates": []
}
```

## Модельная маршрутизация

Без явной директивы router выбирает `luna` для малых задач, `terra` для обычной
инженерной работы и `sol` для архитектуры/security. Fallback разрешён только при
ошибке доступности модели до execution/mutation. Не меняй route ради обхода ограничений.
